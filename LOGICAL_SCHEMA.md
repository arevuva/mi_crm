# Логическая схема приложения — mi_crm

Цель файла: описать предметную (логическую) модель и основные процессы так, чтобы по ней было удобно рисовать схему (не привязываясь к физической БД/Flutter-коду).

## Текст для отчета (Word-ready)

### 1. Предметная область и цель
Система предназначена для ведения процессов компании в едином приложении: управление продажами и товарным учетом, документами, PR/SMM активностями, коммуникациями сотрудников и базовым финансовым учетом. Концептуально система строится вокруг “Компании” и ее структуры (отделы, должности, сотрудники), а функциональность разнесена по модулям CRM.

### 2. Акторы и роли
- Пользователь — учетная запись для входа (email/пароль).
- Сотрудник — профиль человека внутри компании; привязывается к пользователю по email.
- Администратор — пользователь/сотрудник, который конфигурирует CRM (компания, модули, роли).

### 3. Логическая модель доступа
Доступ к разделам приложения определяется:
1) включенными модулями компании (администратор),
2) правами должности сотрудника (список модулей + подмодулей),
3) фактом привязки пользователя к сотруднику (иначе вход в CRM ограничен).

### 4. Группировка по модулям (bounded contexts)
Логику удобно отражать как набор контекстов:
- Sales: категории, товары, лиды, записи продаж/приемки.
- Docs: документы и (частично) операции.
- PR/SMM: PR-материалы, SMM-посты, коммуникации/задачи.
- HR: сотрудники/структура (настройка преимущественно в админке).
- Finance: расходы/учет (проводки), а также аналитика/отчеты.

### 5. Ключевые процессы
1) Онбординг компании (админ): создать компанию → включить модули → настроить отделы/должности → создать сотрудников.  
2) Регистрация/вход: пользователь регистрируется только если администратор завел сотрудника с его email → выполняется привязка аккаунта к сотруднику.  
3) Работа: сотрудник видит только разрешенные модули/подмодули и выполняет операции внутри модулей (создание записей/документов/задач).  
4) Отчеты: формируются как агрегирование операционных данных, также учитывают ограничения доступа (какие модули доступны).

## 1) Контекст и акторы

```
                   +----------------------+
                   |      Пользователь    |
                   |  (аккаунт / login)   |
                   +----------+-----------+
                              |
                              v
                   +----------------------+
                   |      Сотрудник       |
                   | (профиль в компании) |
                   +----------+-----------+
                              |
                              v
                   +----------------------+
                   |      Должность       |
                   | (права на модули)    |
                   +----------+-----------+
                              |
                              v
                   +----------------------+
                   |       Компания       |
                   +----------------------+

Актор "Администратор" = пользователь/сотрудник, который использует экран Admin:
создаёт компанию, включает модули, заводит отделы/должности/сотрудников.
```

## 2) Основные доменные сущности и связи

```
Компания
  |-- Отделы (0..*)
  |     |-- Руководитель отдела = Сотрудник (0..1)
  |
  |-- Должности (0..*)
  |     |-- Права: доступные Модули (0..*)
  |     |-- Права: доступные Подмодули (0..*)
  |
  |-- Сотрудники (0..*)
        |-- принадлежит Отделу (1)
        |-- имеет Должность (1)
        |-- может быть привязан к Пользователю (0..1) по email

Модуль CRM (набор функций)
  |-- включен/выключен на уровне компании (админка)
  |-- дополнительно ограничен на уровне должности (права доступа)

Коммуникации
  |-- Сообщение/Задача: отправитель Сотрудник (1) -> получатель Сотрудник (1)

Продажи/Товарка
  |-- Категория товара (0..*)
  |-- Товар (0..*) -> Категория (1)
  |-- Лид (0..*) -> может ссылаться на Товар (0..1)
  |-- Запись продаж (0..*) -> может ссылаться на Товар (0..1)

Документы
  |-- Документ (0..*) -> может ссылаться на Товар (0..1)

PR/SMM
  |-- PR-материал (0..*) -> может ссылаться на Товар (0..1)
  |-- SMM-пост (0..*) -> может ссылаться на Товар (0..1)

Бухгалтерия
  |-- Проводка (0..*) -> ссылка на цель (target_type + target_id)

Операции (глобальные)
  |-- Операция: {sale|purchase|expense}, сумма, описание, владельцы
```

## 3) Модель доступа (права)

Доступ к функциям определяется пересечением:
1) какие модули включены администратором (конфигурация CRM),
2) какие модули и подмодули разрешены должности сотрудника.

```
                 +----------------------+
                 | Конфиг модулей (ON)  |
                 |  администратор       |
                 +----------+-----------+
                            |
                            v
                 +----------------------+
                 |  Разрешения должности|
                 | modules + submodules |
                 +----------+-----------+
                            |
                            v
                 +----------------------+
                 | Итоговый доступ UI   |
                 | (Home/Report фильтр) |
                 +----------------------+
```

## 4) Логическая карта модулей

Список верхнеуровневых модулей:
- `sales` — продажи/приёмка/товары/лиды/записи продаж
- `docs` — операции и документы
- `pr_smm` — PR-материалы и SMM-посты + коммуникации
- `hr` — сотрудники/структура (в основном управление в админке)
- `finance` — расходы/учёт/задачи персонала (частично)

Подмодули (как “разделы внутри модулей”, управляются правами должности):
см. `lib/presentation/constants/module_submodules.dart`.

## 5) Навигация и режимы работы (логически)

```
Старт приложения
  |
  +--> [не авторизован] ---> Login
  |
  +--> [авторизован] -----> Главные вкладки:
           |-- Главная: рабочие модули (по правам)
           |-- Отчёт: показатели/аналитика (по правам)
           |-- Профиль: данные аккаунта/выход

Админка (отдельный экран/режим)
  |-- Создать компанию
  |-- Включить/выключить модули
  |-- Настроить отделы
  |-- Настроить должности (права на модули/подмодули)
  |-- Завести сотрудников (email обязателен)
```

## 6) Ключевые процессы (as-is)

### 6.1 Онбординг компании (админ)
```
Admin
  -> Создать компанию
  -> Включить нужные модули
  -> Создать отделы
  -> Создать должности и назначить права (modules/submodules)
  -> Создать сотрудников (email + отдел + должность)
```

### 6.2 Регистрация пользователя (self-service)
```
Register(email, password)
  -> проверка: существует Сотрудник с таким email
  -> создание Пользователя
  -> привязка Пользователя к Сотруднику (user_id)
```

### 6.3 Вход пользователя
```
Login(email, password)
  -> проверка пользователя
  -> проверка/допривязка к Сотруднику по email
  -> вход в вкладки
```

### 6.4 Работа в модуле (общий шаблон)
```
Главная/Отчёт
  -> выбрать модуль (видно только разрешённые)
  -> выполнять операции модуля:
       - создать/обновить сущность (товар, документ, запись продаж, задача...)
       - при необходимости указать владельцев (owner_ids)
  -> данные доступны в отчетности/виджетах/списках
```

### 6.5 Коммуникации/задачи между сотрудниками
```
Сотрудник A -> создать сообщение/задачу -> Сотрудник B
  -> (kind=message|task)
  -> статусы задачи: open/...
  -> комментарий/обновления статуса
```

## 7) Что важно для схемы “как рисовать”

Если рисовать одну “главную” логическую схему, обычно удобно выделить 4 блока:
1) Акторы и доступ (Пользователь -> Сотрудник -> Должность -> Права).
2) Модули как bounded contexts (Sales / Docs / PR-SMM / HR / Finance).
3) Общие сущности компании (Company/Departments/Employees/Positions).
4) Сквозные процессы: аутентификация, коммуникации, отчётность.

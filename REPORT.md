# Отчет по проекту `mi_crm`

## 2. Цели и задачи системы
- Централизовать ключевые процессы небольшой компании в одном приложении.
- Обеспечить работу без сервера и сети (локальная БД на устройстве).
- Разграничить доступ к функциональности по ролям (должностям) и включенным модулям.
- Дать администратору инструмент конфигурирования структуры компании и модулей.

## 3. Технологический стек
- Клиент: Flutter (Dart), UI на Material.
- Управление состоянием: `flutter_bloc` (Bloc/Cubit).
- Локальное хранилище: SQLite через `sqflite` (на Linux/Windows — `sqflite_common_ffi`).
- Локальные настройки/сессия: `shared_preferences` (кеш `user_id`).

## 4. Архитектура приложения (высокий уровень)
### 4.1 Архитектурный стиль
Проект построен по слоистой архитектуре:
1) Presentation (экраны/виджеты) — UI и обработка действий пользователя.  
2) State (Bloc/Cubit) — состояние и сценарии (use-cases).  
3) Data (Repositories/Models/LocalDatabase) — доступ к данным и хранение в SQLite.

Принцип: UI не обращается к SQLite напрямую — доступ идет через state-слой и репозитории.

### 4.3 Точки входа и DI
- `lib/main.dart` — инициализация Flutter и включение SQLite FFI на Linux/Windows.
- `lib/app.dart` — composition root: создание репозиториев и регистрация Bloc/Cubit через `MultiRepositoryProvider`/`MultiBlocProvider`.

### 4.4 Структура проекта (логически)
- `lib/presentation/` — экраны и UI-компоненты (`screens/`, `widgets/`, `utils/`, `constants/`).
- `lib/blocs/` — state management (Bloc/Cubit + state/event).
- `lib/data/` — модели, репозитории и локальная БД (`local/`).

### 4.5 State management: основные блоки
Связка “Bloc/Cubit → Repository → LocalDatabase”:
- Auth: `AuthBloc` → `AuthRepository` (users + привязка к employee по email).
- Operations: `OperationsBloc` → `OperationRepository` (операции).
- Report: `ReportCubit` → `OperationRepository` (агрегация операций для показателей).
- Modules: `ModuleCubit` → `ModuleRepository` (включение/порядок модулей).
- Company: `CompanyCubit` → `CompanyRepository` (компания/отделы/должности/сотрудники).
- Sales: `SalesCubit` → `SalesRepository` (категории/товары/лиды/записи продаж).
- Documents: `DocumentCubit` → `DocumentRepository` (документы).
- PR/SMM: `PrCubit` → `PrRepository` (PR-материалы и SMM-посты).
- Accounting: `AccountingCubit` → `AccountingRepository` (проводки).
- Employee communications: `EmployeeCommunicationRepository` (сообщения/задачи между сотрудниками; используется из UI).
- UI-only: `ThemeCubit`, `TabCubit`.

### 5.4 Экран `HomePage` (Главная): структура и разделы
Назначение: рабочее место сотрудника. Экран показывает доступные CRM-модули и их содержимое с учетом:
- включенности модулей в конфигурации компании,
- прав должности (`Position.modules` и `Position.submodules`),
- привязки пользователя к сотруднику (по email).

Основная логика отображения:
- Если компания не создана → сообщение “создайте компанию в режиме администратора”.
- Если нет сотрудника для текущего пользователя → сообщение о необходимости привязки email администратором.
- Иначе:
  - Вверху: список карточек модулей (“Модули CRM”), отфильтрованный по правам.
  - Ниже: содержимое выбранного модуля или обзор.

Адаптивное поведение (responsive):
- Широкий экран (≈ `>= 900px`): модуль выбирается “внутри страницы” (inline), содержимое показывается ниже списка модулей.
- Узкий экран: по нажатию на модуль открывается отдельная страница модуля (через `Navigator.push`), внутри — тот же контент.

Структура модулей на главной (верхний уровень → вкладки внутри модуля):
- `sales` (“Товарооборот”):
  - `Продажи`: фиксация продаж/поступлений, выбор товара, количество/цена/итог, привязка к лиду, список записей продаж.
  - `Приёмка`: оформление прихода/закупок (в т.ч. с поставщиком), создание записи, списки.
  - `Регистрация товара`: создание категорий и товаров (цена, складские остатки), просмотр списков.
  - `Лиды и поставщики`: управление лидами/поставщиками, статусы, создание/выбор, списки.
- `docs` (“Документация”):
  - `Операции`: отображение и работа с операциями/записями (в связке с документами/продажами).
  - `Документы`: добавление/просмотр документов (например, договор/акт), фильтрация по типам.
- `pr_smm` (“PR / SMM”):
  - `Соцсети`: создание/просмотр SMM-постов (канал, текст, статус).
  - `Коммуникации`: переписка/задачи между сотрудниками, назначение сроков/статусов.
- `finance` (“Бухгалтерия”):
  - `Персонал`: учет проводок/изменений по сотрудникам (target_type = `employee`).
  - `Операционные расходы`: учет расходов (target_type = `expense`).
- `hr` (“Управление персоналом”):
  - `Сотрудники`: список сотрудников, статусы, должности, отделы (для руководителей/HR).

Контроль доступа внутри модуля:
- Если для модуля определен список подмодулей в должности и он пуст → выводится сообщение, что нет доступных подмодулей.
- Если список подмодулей не задан → по умолчанию доступны все вкладки модуля.

Источники данных (state):
- `CompanyCubit` — компания, должности, отделы, сотрудники.
- `ModuleCubit` — включенность модулей и порядок.
- `SalesCubit`, `DocumentCubit`, `PrCubit`, `AccountingCubit` — доменные данные по компании.
- `OperationsBloc` — список операций.

### 5.5 Экран `ReportPage` (Отчёт): структура и детализация
Назначение: аналитика и сводные показатели по доступным модулям.

Проверки перед показом отчетов:
- Если нет компании или пользователь не авторизован → заглушка “нет данных для отчётов”.
- Если не найден сотрудник по email → заглушка.
- Если нет должностей → заглушка.

Основной экран отчётов:
- Сетка карточек (tiles) по доступным модулям (включенные ∩ разрешенные должностью).
  - Для `sales` показывается сумма продаж (`salesTotal`).
  - Для `finance` показывается сумма расходов (`expenseTotal`).
  - Для прочих — количество операций/записей.
- Pull-to-refresh (`RefreshIndicator`) вызывает `ReportCubit.refresh()` и пересчитывает агрегаты по операциям.
- Блок “Календарь задач”:
  - Загружает задачи из коммуникаций.
  - Если сотрудник — руководитель (`Position.isHead`), показывает задачи по всему отделу (получатели = сотрудники отдела).
  - Позволяет выбрать день и просмотреть список задач на дату.
- Информационный блок “Советы”.

Детальный отчет по модулю (`_ModuleReportPage`, открывается по нажатию на tile):
- Общий header: название модуля + итоговый показатель (сумма/кол-во).
- Ветвление по модулю:
  - `sales`:
    - Переключатель “Продажи / Поступления”.
    - Графики/сводки за последние дни (агрегация по дням).
    - Разбивка по товарам (в т.ч. выбранный день).
  - `finance`:
    - Мини-график расходов по дням (7 дней).
    - Список финансовых записей (операции + связанные проводки/учет).
  - `docs`:
    - Список документов с фильтром по типу и сортировкой (новые/старые).
    - Отображение участников документа по `owner_ids` (имена сотрудников).
  - `hr`:
    - Список сотрудников с деталями: статус, email, должность, отдел (и отметка “глава” при `is_head`).
  - прочие:
    - Сводки по операциям: агрегация по дням и типам.

## 6. Логическая модель (предметная область)
### 6.1 Акторы и роли
- Пользователь — учетная запись (email/пароль).
- Сотрудник — профиль внутри компании; привязка к пользователю по email.
- Администратор — пользователь/сотрудник, конфигурирующий CRM (компания, модули, роли).

### 6.2 Сущности и связи (логически)
```
Компания
  |-- Отделы (0..*)
  |     |-- Руководитель отдела = Сотрудник (0..1)
  |
  |-- Должности (0..*)
  |     |-- Права: доступные Модули (0..*)
  |     |-- Права: доступные Подмодули (0..*)
  |
  |-- Сотрудники (0..*)
        |-- принадлежит Отделу (1)
        |-- имеет Должность (1)
        |-- может быть привязан к Пользователю (0..1) по email

Модуль CRM (набор функций)
  |-- включен/выключен на уровне компании
  |-- дополнительно ограничен правами должности
```

### 6.3 Модель доступа (права)
Доступ к функциональности определяется пересечением:
1) включенных администратором модулей,  
2) разрешений должности сотрудника (модули + подмодули).

```
                 +----------------------+
                 | Конфиг модулей (ON)  |
                 |  администратор       |
                 +----------+-----------+
                            |
                            v
                 +----------------------+
                 |  Разрешения должности|
                 | modules + submodules |
                 +----------+-----------+
                            |
                            v
                 +----------------------+
                 | Итоговый доступ UI   |
                 | (Home/Report фильтр) |
                 +----------------------+
```

### 6.4 Модули CRM (верхний уровень)
- `sales` (Продажи) — продажи, приемка, товары, лиды, записи продаж.
- `docs` (Документация) — операции и документы.
- `pr_smm` (PR/SMM) — PR-материалы, SMM-посты, коммуникации.
- `hr` (Управление персоналом) — сотрудники/структура (в основном настройка в админке).
- `finance` (Бухгалтерия) — учет/расходы/проводки и показатели.

### 6.5 Подмодули (разделы внутри модулей)
Подмодули используются для более детального контроля доступа на уровне должности:
```
sales:
  - sales (Продажи)
  - intake (Приёмка)
  - product_registration (Регистрация товара)
  - leads (Лиды и поставщики)

docs:
  - operations (Операции)
  - documents (Документы)

pr_smm:
  - social (Соцсети)
  - communications (Коммуникации)

finance:
  - employee (Персонал)
  - expense (Операционные расходы)

hr:
  - employees (Сотрудники)
```

## 7. Хранилище данных (SQLite)
### 7.1 Подход к данным
- Все данные хранятся локально, схема создается и мигрирует в `LocalDatabase`.
- Связи между сущностями заданы логически через `*_id` (без явных `FOREIGN KEY`).
- `owner_ids` хранится в виде CSV-строки.

### 7.2 ER-диаграмма базы данных (ASCII)

## 8. Основные пользовательские потоки
### 8.1 Онбординг компании (администратор)
1) Создание компании.  
2) Включение/отключение модулей.  
3) Создание отделов.  
4) Создание должностей и назначение прав (модули/подмодули).  
5) Создание сотрудников (email, отдел, должность).  

### 8.2 Регистрация/вход пользователя
- Регистрация возможна только если администратор предварительно создал сотрудника с данным email.
- После регистрации/входа выполняется привязка пользователя к сотруднику.

### 8.3 Работа и отчетность
- На Главной показываются модули, разрешенные должностью и включенные в конфигурации компании.
- Отчеты агрегируют данные и также учитывают доступ по модулям.

## 9. Выводы и направления развития
- Архитектура проекта подходит для offline-first сценария и расширения по модулям (через добавление репозиториев/Bloc и таблиц).
- Для усиления целостности данных можно добавить явные `FOREIGN KEY` и нормализовать связи `owner_ids` (таблица связей many-to-many).
- При переходе к серверной архитектуре целесообразно сохранить интерфейсы репозиториев и заменить реализацию `LocalDatabase` на API-слой.

## 10. Точки расширения (как развивать систему)
### 10.1 Добавление нового модуля CRM
1) Добавить модуль в список дефолтных модулей (логика модуля + отображение).
2) При необходимости — описать подмодули (для детализации прав).
3) Добавить нужные сущности/таблицы в `LocalDatabase` и CRUD в репозитории.
4) Добавить Bloc/Cubit и UI-экран(ы), подключить к Home/Report.

### 10.2 Переход к серверной архитектуре
Рекомендуется сохранить интерфейсы репозиториев как “контракт” слоя данных и заменить реализацию SQLite (`LocalDatabase`) на API-клиенты с кешированием.
